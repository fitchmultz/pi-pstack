# Opinion model contract

`pstack_opinion` is a single text consultation, not a second tool-using Pi agent. This inventory separates what the code enforces from what the prompt asks the model to do. The card renderer does not change this contract.

## Scope and sources

The line references below point to the [audited tool registration in `extensions/index.js`][call]. The card renderer affects only display. On Fitch Pi, deferred exposure controls how the parent model reaches the tool. It does not add tools to the opinion request.

The exact hosts for qualification are official Pi **1.7.0** and Fitch Pi **91b90ac7dbd18f530d413b5b5f0a1768693cf5c8**, as pinned by `package.json` and `scripts/qualify-hosts.mjs`, respectively. A registered provider can have its own server-side behavior. Omitting Pi tools is not a sandbox around provider code or its service.

## What is not limited by pstack

There is no pstack-specific input length, answer length, token, time, cost, concurrency, model-family, or provider allowlist in this call. No `maxTokens`, temperature, timeout, or extra retry loop is installed at `extensions/index.js:253–256`. This is not a claim of unlimited service: context windows, output limits, reasoning support, request authentication, provider policies, and native transport behavior still apply.

The model can analyze supplied code, propose edits in text, identify contradictions, perform reasoning, and discuss supplied test output. Pstack cannot guarantee correctness, require exclusive reliance on the supplied material, or prevent a configured provider from implementing capabilities on its own server. It offers no host execution mechanism for actions proposed in the answer.

## Findings and minimal recommendations

These are recommendations only. The renderer change does not implement them or alter the limitation set.

1. **Overbroad prompt wording.** At `extensions/index.js:254`, replace “cannot … verify an application” with “cannot independently inspect or execute the application; you can analyze only the evidence supplied here.” Keep the distinction between reviewing evidence and performing live verification.
2. **Redundant but useful orientation.** “You have no tools” at line 254 repeats the enforced no-tools request. It is not the enforcement mechanism. Keeping the sentence helps avoid misleading claims; no new guard is needed.
3. **Incomplete-stop reporting.** `extensions/index.js:259–264` rejects only `error`, `aborted`, and `toolUse`. A native `length` response retains its text and names `length`, but is not marked as an error, so the background envelope calls it completed. Native types also include `pending` and `deferred`; this tool does not request deferred mode or implement handle recovery. Recommend explicitly describing an output-limit response as incomplete while preserving its text, and reporting unsupported nonfinal outcomes rather than implying a finished opinion. Do not add an agent loop or custom provider recovery. This is a source-level finding, not a claim that every provider returns these outcomes here.
4. **Lossy unsuccessful answers.** Lines 259–261 discard any partial text on an error, abort, or tool-use stop. If partial analysis is valuable, return it alongside the error without treating it as complete. That would be a separate output-policy decision.

No arbitrary numeric cap or selective tool exclusion was found. Text-only input, explicit model selection, and a single non-tool response are product choices supported by the documented purpose. They should not be silently expanded as part of a rendering fix.

## Completion-card contract

Both supported hosts expose `registerMessageRenderer(customType, renderer)`. Their [official renderer contract][official-renderer] and [fork renderer contract][fork-renderer] pass the message, `expanded`, `outputPad`, and keybinding hints. The fork also passes boolean `compactView` and wraps collapsed custom-message output in its native two-row `CompactPreview`; official Pi omits `compactView`.

Custom-message cards cap collapsed body previews at **5 visual lines** via the public `truncateToVisualLines` helper after Markdown layout so a long paragraph cannot evade the cap by wrapping. The title row, box padding, and collapsed expand-hint row sit outside the five body lines, and the expand hint appears only when lines are omitted (`skippedCount > 0`). Terminal escape sequences and unsafe C0/C1 control characters are stripped before Markdown rendering. On the fork, `CompactPreview` reduces collapsed cards in compact view to two nonempty rows (title plus first body row), while expanded cards show the full Markdown in every view. Fitch Pi's compact Activity group can also hide the card until the group is opened.

Only presentation is shortened. The original custom-message content remains unchanged in the journal and model context. Ctrl+O uses Pi's native `app.tools.expand` action, including remapped key hints. Left-clicking an opinion card toggles only that card. On Fitch Pi, which passes a boolean `options.compactView`, the [custom message component][fork-message] handles the click in every view. On official Pi, the [custom message component][official-message] inherits `Container.handleMouse`, which forwards clicks to the renderer's `MouseRegion`. The region toggles per-message state in a `WeakMap`. A change in global expansion resets that state. There is no new keyboard parser or stored opinion copy.
